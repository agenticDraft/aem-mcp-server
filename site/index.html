AEM MCP Server (mTLS fork)

A client's AEM sat behind a Dispatcher that demanded a client certificate, and the server could not present one. This fork adds that, and closes two network holes found on the way.

Public repo: https://github.com/agenticDraft/aem-mcp-server

What this fork adds

What this fork adds

Against upstream release 1.7.1 the fork touches 20 files: 2,426 lines added, 25 removed. About half of that is tests.

Who calls what

Server → Dispatcher → AEM

The certificate changes the connection. The login stays as it was.

  • Client certificates (mTLS) PR #1

    --cert, --key and --ca let the server present a client certificate to AEM. It works with Basic and OAuth, on both transports, and for every entry in --instances. Env fallbacks: AEM_CERT_PATH, AEM_KEY_PATH, AEM_CA_PATH; the key passphrase is env only (AEM_KEY_PASSPHRASE).

    New module src/aem/aem.cert-fetch.ts (280 lines), small edits in aem.fetch.ts, aem.connector.ts, mcp.instances.ts, cli.ts.

  • HTTP transport listens on 127.0.0.1 PR #5

    New flag --mcpHost (env MCP_HOST), default 127.0.0.1. Before, app.listen(port) bound every interface. This is a breaking change for anyone who reached /mcp from another machine.

  • Origin header validation PR #6

    A request carrying a browser Origin that is not loopback and not on the allowlist gets 403. New flag --allowedOrigins (env MCP_ALLOWED_ORIGINS). The blanket cors({ origin: '*' }) is gone. Logic lives in src/server/app.origin.ts, pure functions, no Express.

  • Documentation PR #2–#4, #7

    A README section on mTLS with its limits, a "What this fork adds" section that separates this work from upstream, and a public explainer of authentication and client certificates.

Why

A gate the server could not pass

The first change came from a client requirement. The other two came from reading what the HTTP transport exposed.

  • mTLS: every tool failed before AEM was reached

    When a Dispatcher or CDN runs SSLVerifyClient require, a client without a certificate fails at the TLS handshake. Node's global fetch has no way to attach client TLS material, so no tool could work, whatever the credentials.

  • Loopback: /mcp has no authentication

    The Basic-auth middleware in app.server.ts is commented out. Listening on every interface therefore exposed AEM operations, under the configured AEM credentials, to anything that could reach the port. Loopback by default closes that unless the operator opts out with --mcpHost.

  • Origin: a local server is still reachable from a web page

    The MCP Streamable HTTP specification says servers must validate Origin to prevent DNS rebinding and answer 403 when it is present and invalid. Binding to loopback does not stop a browser tab from calling it.

The certificate is not an authentication mode. It secures the connection from this server to AEM, and AEM still authenticates the user. So -u/-p or -i/-s are passed alongside it, exactly as without a certificate.

How mTLS fits

One seam, no change when off

AEMFetch already wraps a transport. The fork splits header building from the transport and swaps only the transport.

  • Why node:https

    The cert transport is https.request over an https.Agent, wrapped to return a standard Response. It adds no dependency. Global fetch stays the transport whenever no certificate is configured.

  • It refuses to start on a configuration that cannot work

    --cert without --key (or the reverse), --ca alone, an unreadable or non-PEM file, a mismatched keypair, an encrypted key without AEM_KEY_PASSPHRASE, or any host that is not https://. Each exits 1 and names the problem. Loopback hosts are exempt from the https:// check.

  • The server certificate is still verified

    --ca is only for an AEM certificate the system does not trust. The harness checks that a wrong --ca fails.

Security rules

What the HTTP transport now enforces

All of it applies only to -t http. Stdio is unchanged.

  1. Bind to 127.0.0.1.

    Pass --mcpHost 0.0.0.0 only behind your own access control.

  2. No Origin header, allowed.

    Non-browser clients send none, so Claude Code, Cursor and scripts keep working.

  3. Loopback origins, allowed.

    localhost, 127.0.0.1 and [::1], on any port.

  4. Anything else needs an exact match.

    Listed in --allowedOrigins as scheme://host[:port]. Everything else gets 403.

  5. A typo fails at startup.

    An entry with a path or no scheme throws instead of silently blocking the client it was meant to allow.

  6. CORS reflects, never *.

    Only origins that passed the check are echoed back.

  7. * switches the check off.

    An explicit opt-out for setups that have their own gateway.

Tests

A real handshake, no AEM needed

Unit tests run in npm test. The handshake tests are opt-in because they generate certificates and bind ports.

  • test/aem.cert-fetch.test.js

    31 test cases by my count of test(/it( calls. Every validation failure path and the "no certificate configured" contract.

  • test/app.origin.test.js

    10 test cases on the Origin rules.

  • test/manual/e2e-cert.mjs

    One command. Generates a throwaway CA and certificates, starts a stub mTLS server, drives dist/cli.js over stdio and HTTP, and stops every child it started. It covers the startup errors, Basic plus certificate on the same request, an encrypted key, negative controls (no certificate, a certificate from another CA), a one-hop redirect, two instances each presenting the certificate to its own host, and 200 calls with a flat file-descriptor count.

  • test/manual/regression-auth.mjs

    Proves that with no certificate, Basic and OAuth behave as before: exact Authorization values, one retry on 401. With --baseline it compares every request against a build of main.

  • smoke-oauth-cert.mjs · smoke-cert-fetch.mjs

    OAuth plus certificate against a faked IMS, and the transport on its own.

The harness cannot run inside a network sandbox.

Limits

What it does not do

Stated in the README, repeated here so nobody finds them by surprise.

  • Not published yet

    npx aem-mcp-server installs the upstream release 1.7.1, which has no --cert, --mcpHost or --allowedOrigins. To use them, clone this fork, run npm ci && npm run build and start node dist/cli.js.

  • Breaking change

    Remote setups that reached /mcp over the network must now pass --mcpHost, and browser callers need --allowedOrigins.

  • Scope of the certificate

    It protects the connection to AEM. It does not protect this server's own /mcp endpoint, which still has no authentication.

  • Rotation

    Certificates are read once at startup. Replacing the files has no effect until the process restarts.

  • Redirects and revocation

    In certificate mode one redirect hop is followed, not a longer chain. There is no CRL or OCSP check; handle revocation at the Dispatcher or CDN.

  • No indicator

    Nothing is logged for "mTLS enabled" and /health is unchanged. A process that started has valid material. A certificate AEM rejects fails on the first tool call.

Not part of this fork

What came from upstream

Most of the project predates this fork. The README now says so.

The 57 tools, MCP resources, Content and Experience Fragment managers, multi-instance support, the Zod schemas and mergeJsonField are upstream work by Dragan Filipović and other contributors to easingthemes/aem-mcp-server. This fork adds the three changes above and their tests and docs.
